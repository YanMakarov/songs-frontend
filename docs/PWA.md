# PWA: оболочка, обновления, установка

Фаза 7.1 роадмапа. Данные и до этого были офлайновыми — кеш React Query в
IndexedDB (фаза 2). Не хватало ровно одного: **оболочки**. Без service worker
открытие приложения без сети упиралось в «нет подключения» раньше, чем
кеш успевал что-то показать.

## Что где

| Файл | Роль |
|---|---|
| `vite.config.js` → `VitePWA({...})` | манифест, precache, стратегия обновления |
| `src/components/PwaUpdateBanner.jsx` | регистрация SW + баннер «Есть новая версия» |
| `public/pwa-*.png`, `public/favicon.svg` | иконки (сгенерированы, см. ниже) |
| `index.html` | `theme-color`, apple-мета, иконки |
| `src/lib/theme.js` → `syncThemeColor` | цвет статус-бара под выбранную тему |

Сборка кладёт рядом с `dist/index.html` файлы `sw.js`, `workbox-*.js` и
`manifest.webmanifest`. Деплой не меняется: `deploy/deploy-frontend.sh`
синхронизирует весь `dist/`.

## Что кешируется, а что нет

Precache — только оболочка: `index.html`, JS, CSS, иконки, манифест
(~430 КБ). Любой внутренний маршрут офлайн разрешается в `index.html`
(`navigateFallback`), как это делает nginx, когда сеть есть.

**Запросы к API service worker не кеширует — намеренно.** Песни и так живут
офлайн в персистентном кеше React Query, и именно он знает про `rev`, ETag,
очередь записи и мердж. Второй кеш в SW умеет отдать приложению устаревшее
тело — а на нём строится `If-Match`, то есть ценой была бы молча потерянная
правка. В проде API вообще на другом домене (`songs-api.it-slon.ru`), так что
SW его запросы и не видит; `navigateFallbackDenylist` закрывает тот же вопрос
для дев-прокси, где `/setlists` лежит на том же origin.

## Обновления

`registerType: 'prompt'`, не `autoUpdate`. Новая сборка **никогда** не
перезагружает вкладку сама: на сцене это стёрло бы экран посреди песни, а в
редакторе — устроило бы гонку с очередью записи. Вместо этого появляется
баннер «Есть новая версия · Позже · Обновить», и перезагрузка происходит
только по тапу. До тапа продолжает работать старая оболочка.

Открытая вкладка проверяет наличие новой сборки раз в час и при возврате
фокуса — по той же логике, что и синхронизация сетлиста в `lib/sync.js`:
ничего не делаем, пока вкладка скрыта или устройство офлайн.

### Заголовки на сервере (nginx)

Обязательное условие того, что обновление вообще доедет:

```nginx
location = /sw.js {
  add_header Cache-Control "no-cache";
}
location = /index.html {
  add_header Cache-Control "no-cache";
}
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
```

Имена файлов в `assets/` содержат хеш, поэтому их можно кешировать вечно.
`sw.js` и `index.html` — нельзя: закешированный на сутки `sw.js` означает
сутки со старой версией у всех, кто уже открывал приложение.

## Установка на устройство

Кнопка «Установить» живёт в настройках приложения
(`src/components/InstallSection.jsx` поверх `src/lib/install.js`). Четыре
разных текста вместо одной кнопки — потому что установку по-настоящему
предлагает только Chromium:

| Состояние | Что видит человек |
|---|---|
| Chromium, установка доступна | кнопка «Установить» |
| Уже установлено (запуск с рабочего стола) | «Установлено. Песни открываются…» |
| iOS | «В Safari: „Поделиться“ → „На экран «Домой»“» |
| Остальное | «В меню браузера выберите „Установить приложение“» |

`beforeinstallprompt` срабатывает один раз за загрузку страницы и очень рано —
обычно до того, как смонтируется React. Поэтому событие перехватывается на
уровне модуля (`lib/install.js` импортируется из `main.jsx` ради этого сайд-
эффекта) и потом отдаётся тому, что отрисуется позже. `event.preventDefault()`
гасит собственную плашку браузера — цена того, чтобы кнопка была там, где ей
место, рядом с остальными настройками.

На iOS предложить установку невозможно в принципе: Safari не даёт ни события,
ни API. Отсюда определение платформы — с учётом того, что iPad на iPadOS 13+
представляется маком, и выдаёт его только `maxTouchPoints`.

## Постоянное хранилище

`navigator.storage.persist()` просит браузер не выбрасывать IndexedDB, когда
на телефоне кончается место, — а это ровно тот кеш, из которого приложение
читает без сети. Запрашивается в двух точках: при запуске с рабочего стола и
сразу после установки. В обычной вкладке — нет: там человек ещё ничего не
решил.

Движки отвечают на этот вопрос по-разному, и из этой разницы вся логика:
Chromium решает молча, исходя из вовлечённости и факта установки, поэтому
повторить запрос на следующем запуске бесплатно и он вполне может пройти там,
где не прошёл первый. Firefox превращает вызов в диалог разрешения — там
спрашиваем ровно один раз за всё время (флаг `chords_app_storage_persist_asked_v1`).
Safari `persist()` не поддерживает, но приложению с домашнего экрана и так не
грозит семидневная чистка ITP, которая стирает данные обычных вкладок.

## Иконки

`public/pwa-192.png`, `pwa-512.png`, `pwa-maskable-512.png` (аппликатура на
сине-фиолетовом градиенте), `apple-touch-icon.png` (180×180, непрозрачный
квадрат — маску iOS накладывает сам), `favicon.svg` + `favicon-32.png`.

Maskable — отдельный файл, а не `purpose: 'any maskable'` на общем: лаунчер
обрезает maskable-иконку до ~80 %, и общий файл потерял бы края. Рисунок в
нём уменьшен, чтобы целиком попасть в safe zone.

Конвертеров SVG в системе не оказалось, и ставить их ради четырёх статичных
файлов смысла нет, поэтому PNG рисует `scripts/make-icons.py` — голый Python
(`zlib` плюс рендер в 4× с последующим усреднением, иначе тонкие линии струн
рябят). Перерисовать после правки цветов или рисунка:

```bash
python3 scripts/make-icons.py
```

`favicon.svg` — та же картинка вручную в векторе, чтобы вкладка была чёткой
на любом экране; его правят отдельно.

## Как проверять

Дев-сервер по умолчанию **без** service worker: SW в дев-режиме кеширует
модули и превращает «почему правка не видна» в полчаса поисков. Для проверки
install/update:

```bash
VITE_PWA_DEV=true npm run dev
```

Более честный способ — собрать и поднять статику:

```bash
npm run build && npm run preview -- --port 4173
```

Проверено на превью-сборке: SW регистрируется и активируется, precache
содержит 11 файлов, при **остановленном** сервере и `/songs/{id}` в адресной
строке приложение открывается из кеша и показывает песню; новая сборка даёт
баннер, тап по «Обновить» активирует её и перезагружает вкладку. Блок
установки проверен во всех четырёх состояниях (подменой события и
user-agent): кнопка вызывает `prompt()` и исчезает, `appinstalled` переводит
блок в «Установлено», на iOS-агенте показывается инструкция про «Поделиться».

## Прод: снимите Basic auth со статики

Раньше `https://songs.it-slon.ru` был закрыт nginx-ом за Basic auth — 401
отдавался и на `/`, и на `/manifest.webmanifest`, и на `/sw.js`. Установить
приложение при этом формально можно, но каждый холодный запуск с рабочего
стола упирался в диалог логина без адресной строки и вкладок, а Chrome в таком
состоянии часто вовсе не предлагал установку. Защищал этот пароль при этом
немногое: API отвечал без всякой авторизации, то есть данные были доступны в
обход фронта.

Теперь авторизация живёт в самом API (см. `backend/README.md`), и Basic auth
со статики нужно снять — иначе она продолжает ломать установку, ничего больше
не закрывая. Статика после этого публична, и это правильно: в ней нет данных,
только оболочка, которая на первом же запросе получит 401 и покажет экран
входа.

Про офлайн стоит помнить одно. Приложение сознательно **не** отправляет на
экран входа из-за недоступного сервера: холодный старт без сети рисует песни
из IndexedDB и показывает внизу «Офлайн — вход не проверен». На экран входа
уводит только явный ответ сервера. Иначе репетиция в подвале начиналась бы с
формы логина, которую некуда отправить.

Долго так продолжаться не может: если сервер не подтвердил сессию 30 дней
подряд, локальная копия стирается и вход становится обязательным — см.
`UNVERIFIED_GRACE_MS` в `src/lib/auth.jsx`.
