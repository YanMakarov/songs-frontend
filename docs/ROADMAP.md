# План: кеш, синхронизация, локальный режим, отмена

Живой документ. Отмечайте сделанное прямо здесь.
Веб-версия с подробностями: https://claude.ai/code/artifact/b55154cf-ebe4-41cb-bfae-bdf7d074bfc2

## Несущая идея

Всё держится на одном числе. У сетлиста есть монотонный счётчик `rev_counter`;
каждая запись песни забирает следующее значение и складывает его себе в `Song.rev`.
Дальше это же число работает как:

| Роль | Где |
|---|---|
| Версия песни | `ETag: W/"<id>-<rev>"`, `If-Match` при записи |
| Ключ инвалидации кеша | сравнение `rev` в IndexedDB с серверным |
| Курсор ленты изменений | `GET /setlists/{slug}/changes?since=<rev>` |
| Базовая версия для мерджа | `SongRevision.rev` (фаза 4) |

Поэтому фазы 0 и 1 — не подготовка «на будущее», а фундамент: без `rev`
остальные четыре задачи пришлось бы решать четырьмя разными механизмами.

## Чего в плане нет — намеренно

- **WebSocket.** Двусторонний канал нужен для presence и курсоров. Для «увидеть
  чужую правку через полминуты» он требует хаб, sticky sessions, свой heartbeat
  и свой реконнект — ради того, что делает один GET по возврату фокуса.
  Если задержка когда-нибудь станет критичной, следующий шаг — **SSE, а не WS**:
  `Last-Event-ID` это уже готовый `since`, а записи остаются на REST.
- **CRDT (Yjs, Automerge).** Оправдан, когда двое печатают в один абзац
  одновременно. У группы такого сценария нет, а цена — переезд модели хранения.
- **Опрос по таймеру в фоне.** Батарею сажают частые пробуждения радиомодуля,
  а не соединение само по себе. Опрос идёт только пока вкладка видима.
- **localStorage для контента.** Синхронный доступ блокирует главный поток,
  лимит ~5 МБ. Контент — в IndexedDB, в localStorage только настройки интерфейса.

## Фаза 1 — Версии и мягкое удаление ✅

- [x] **1.1 Схема.** `Setlist.rev_counter`, `Setlist.purged_rev`, `Song.rev`,
      `Song.updated_by`, `Song.deleted_at`. Одно число вместо двух: `rev`
      уникален в пределах сетлиста и монотонно растёт, поэтому годится и как
      версия песни, и как позиция в ленте. Бэкфилл — по `rowid`.
- [x] **1.2 Присвоение rev и мягкое удаление.** `crud._next_rev()` в той же
      транзакции, что и запись. `delete_song` проставляет `deleted_at` вместо
      `session.delete`; `list_songs` фильтрует удалённые.
- [x] **1.3 Условные запросы.** GET песни отдаёт `ETag: W/"<id>-<rev>"` и `304`
      на совпавший `If-None-Match`; PATCH/DELETE требуют `If-Match` →
      `412` с телом `{ current: SongDetail }`, чтобы не ходить за состоянием
      вторым запросом. `Cache-Control: no-cache` — это «храни, но перепроверяй»,
      а не отключение кеша.
- [x] **1.4 Лента изменений.** `GET /setlists/{slug}/changes?since=N` отдаёт
      только изменившееся; `GET /setlists/{slug}/state` — полный список
      `{id, rev}` для холодной сверки, когда клиент отстал или потерял курсор.
- [x] **1.5 Восстановление.** `POST /songs/{id}/restore` снимает `deleted_at`
      и выдаёт новый `rev`. `GET /songs/?deleted=1` — корзина.
      Чистка старше 30 дней двигает `purged_rev`, чтобы лента честно отвечала
      `tooOld` тем, кто отстал слишком сильно.
- [x] **1.6 Клиент: минимальная поддержка.** Хранить `rev`, слать `If-Match`,
      на `412` показывать «Песню изменил X — Обновить». Настоящий мердж —
      фаза 4; до тех пор честная перезагрузка лучше молчаливой перезаписи.

## Фаза 2 — Кеш в браузере ✅

- [x] **2.1** Взять TanStack Query + `persistQueryClient` поверх `idb-keyval`,
      а не писать своё: дедупликация, `staleTime`, обновление по фокусу,
      оптимистичные мутации с откатом. ~13 КБ gzip.
- [x] **2.2** `lib/db.js` (IDB) и `lib/queryClient.js`. `buster` = версия схемы,
      тогда смена формата сама выбрасывает старый кеш. Тема/`viewMode`/
      `textScale` остаются в localStorage; песни и формы — в IDB.
- [x] **2.3** Чтение: `useSongsQuery`, `useSongQuery(songId)`.
      Ручной `If-None-Match` **не понадобился**: бэкенд отдаёт
      `Cache-Control: no-cache`, поэтому браузер и так шлёт условный запрос
      и пропускает тело на `304`. Дублировать это в JS — только возиться
      с пустыми ответами без выигрыша.
- [x] **2.4** Запись: мутации с оптимистичным обновлением и откатом —
      для создания, удаления, восстановления и переупорядочивания.
      **`writeQueue.js` остался** вопреки исходному плану: правка песни идёт
      через него, потому что (а) мутации не умеют дебаунс и слияние, а без
      них был бы запрос на нажатие клавиши, и (б) колбэки мутации,
      запущенной из компонента, не гарантированно срабатывают после его
      размонтирования — а это ровно тот баг, который чинила фаза 0.
      Связывает очередь с кешем `lib/cacheBridge.js`.
- [x] **2.5** Офлайн-запись: правка при недоступном сервере копится в
      очереди и уходит при восстановлении связи (проверено).
      Сохранение самой очереди между перезагрузками — открытый пункт,
      переносится в фазу 5 вместе с черновиками.

**Что выяснилось по ходу.** Два умолчания, которые выглядят разумно и
оказались неверными:

1. `shouldDehydrateQuery: status === 'success'` выбрасывает из кеша запрос,
   последний запрос которого упал, — хотя React Query хранит рядом прошлые
   удачные данные. Одна неудачная фоновая перезагрузка при лежащем сервере
   стирала список песен, и следующий старт показывал пустой экран. Верно:
   сохранять всё, у чего есть `data`.
2. `staleTime` в минуту глушит обновление по фокусу. До фазы 3 фокус —
   единственный способ, которым чужая правка вообще попадает во вкладку,
   так что приложение стало бы менее живым, чем было без кеша. Поставлено
   5 секунд: с ETag перепроверка стоит один условный запрос и пустой `304`.

## Фаза 3 — Синхронизация без сокетов ✅

- [x] **3.2** Когда спрашивать: вкладка стала видимой — сразу; `online` — сразу;

- [x] **3.3** Пустой ответ — ничего. Непустой — точечная инвалидация; открытую

- [x] **3.4** Экспоненциальная пауза до 5 минут, сброс при первом успехе.
- [x] **3.5** Никаких модалок: метка «изменено» в списке (снимается при
      открытии песни), строка «Песню изменили — Имя · Показать» в редакторе.
      Молча применяется только пока нет несохранённых локальных правок —
      `hasPending(songId)` гасит перезапрос, чтобы серверная копия не легла
      поверх неотправленной работы.

**Что выяснилось по ходу.** Возврат фокуса во вкладку поднимает сразу два
события — `visibilitychange` и `focus`, — и к ним может подоспеть таймер.
Все три тика читали курсор до того, как первый успевал его сдвинуть, и
одни и те же изменения выкачивались и применялись по три раза. Лечится
флагом «запрос в полёте»; без него это выглядело как застрявший курсор.

## Фаза 4 — Конфликты ✅

- [x] **4.1** Таблица `SongRevision` со снимками `markdown_body`, обрезка до
      последних 50 на песню. Бесплатно даёт историю изменений.
- [x] **4.2** Мердж на сервере (`merge3`, чистый Python): при несовпадении
      `If-Match` взять снимок предка и слить три версии. Успех — `200` +
      `X-Merged: true`; конфликт — `412` с `{current, base, mine}`.
      **Мерджить текст, а не по id строк**: `markdown_to_lines` генерирует id
      заново при каждом чтении, эти якоря врут.
- [x] **4.3** Метаданные (тональность, темп, заголовок) — LWW, помечать
      перезаписанное поле в ответе.
- [x] **4.4** Ручное разрешение только при реальном пересечении: «оставить мою»,
      «взять его», «показать различия». Дифф рендерить существующим `Line.jsx`.
- [x] **4.5** Известные ограничения построчного diff3:
      - перемещение блока целиком видится как удаление + вставка;
      - **правки в соседних строках тоже дают конфликт** — diff3 объединяет
        изменения только когда между ними есть нетронутая строка. Для
        песенника это заметно: два человека правят подряд идущие строки
        куплета и получают вопрос. Лечится только переходом на CRDT, от
        которого мы отказались осознанно.

**Что выяснилось по ходу.** Пока конфликт не разрешён, фоновая
синхронизация успевала подменить локальную версию — очередь уже сбросила
правку, `hasPending` возвращал false, инвалидация проходила, и в диалоге
обе колонки показывали серверный вариант. Выбирать было не из чего.
Локальная версия теперь снимается в момент конфликта и живёт в его
состоянии, а не читается из кеша.

> **Не путать с замком.** Режим просмотра (замочек в шапке, включён по
> умолчанию) правки запрещает вовсе: тап по аккорду открывает аппликатуру,
> транспонирование работает локально, но ничего не уходит на сервер.
> Локальный режим ниже — противоположное: правь свободно, результат не
> уходит группе, пока не опубликуешь.

## Фаза 6 — Отмена ⬜

> Три бага в текущей реализации:
> 1. **Серия удалений теряется.** Каждое новое удаление затирает предыдущее
>    ожидающее (`App.jsx:112`, `SongEditor.jsx:431`) — из пяти строк отменить
>    можно только последнюю, а баннер пишет «Строка удалена». В списке песен
>    затёртое удаление ещё и *не коммитится*: песня исчезла из интерфейса,
>    но осталась в базе.
> 2. **Таймер для строк ничего не значит.** Удаление уходит на сервер сразу,
>    5 секунд лишь прячут баннер; отмена — обратная операция.
> 3. **Таймер для песен значит слишком много.** Живёт только в памяти: `F5`
>    в течение 5 секунд — удаления не будет вовсе. Уйти со списка — баннер
>    исчезнет, таймер продолжит идти, отменить нечем.

- [ ] **6.1** `useUndoStack` поверх `commitPatch`: `{do, undo, label}`, глубина
      ~50, `Cmd+Z` / `Cmd+Shift+Z`. Тост становится подсказкой, а не дедлайном.
- [ ] **6.2** Группировка: удаления с паузой < 2 с — одна операция, один тост
      «Удалено 5 строк — Отменить», возврат всей группы разом. Восстанавливать
      **по якорю** (id предыдущей уцелевшей строки), а не по индексу.
- [ ] **6.3** Стек всплывашек не делать: несколько тостов сразу — шум, у каждого
      свой отсчёт, прочитать не успевают. Агрегация решает тот же запрос лучше.
- [ ] **6.4** Песни: удалять сразу как `deleted_at`, отмена — `POST /restore`.
      Баг с двумя удалениями подряд исчезает сам.
- [ ] **6.5** Корзина в настройках: что, кем и когда удалено, 30 дней.
      Это тот «путь сделать то же самое без спешки», которого требует любой
      интерфейс с таймером.
- [ ] **6.6** `UNDO_TIMEOUT_MS` может остаться длительностью показа тоста, но
      ни одно решение о данных на него больше не опирается. Это критерий
      готовности фазы.

## Риски

- **`rev` — точка сериализации.** Инкремент обязан идти в той же транзакции,
  что и запись песни. На SQLite с одним процессом безопасно при WAL;
  при переезде на Postgres станет последовательностью.
- **Идентификаторы строк нестабильны.** План их не чинит и намеренно на них
  не опирается. Понадобятся стабильные якоря — писать их в markdown нельзя,
  формат должен остаться человекочитаемым; это будет отдельная таблица позиций.
- **Атрибуция подделывается.** До настоящего входа `updated_by` — удобство
  интерфейса, не гарантия. Ничего критичного на него завязывать нельзя.
- **Фаза 2 переписывает работающий код** — единственная с реальным риском
  регрессии. Делать отдельно и не смешивать с фазой 6, хотя обе трогают
  `App.jsx`.

## Если делать только часть

Фазы **0, 1 и 6** — самый выгодный минимум: закрывают потерю правок,
безвозвратное удаление и всё непонятное в отмене, не трогая архитектуру
фронтенда. Совместная работа остаётся на уровне «обнови страницу», но
перестаёт молча терять данные.
